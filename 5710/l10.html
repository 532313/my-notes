Web 安全

Web security

浏览器会执行网页里的代码，也会自动携带一些登录凭据。Web 场景题先找出哪条边界失守。是用户没同意就修改了状态，还是浏览器把数据当脚本，或者数据库把数据当 SQL？

A browser runs page code and can attach session credentials automatically. In a web security scenario, identify the broken boundary. Did the application perform an action without user intent, did the browser treat data as code, or did the database treat data as SQL?

URL、HTTP 与同源策略

URLs, HTTP and the same-origin policy

读 URL 例子 https://lab.example:8443/items?id=7#notes。协议是 https，主机是 lab.example，端口是 8443，路径是 /items，查询参数 id 是 7，片段 notes 一般由浏览器处理。HTTP 请求有方法、目标和头，某些请求还带正文。服务器用状态码、头和正文返回响应。

Read https://lab.example:8443/items?id=7#notes as scheme https, host lab.example, port 8443, path /items, query value id=7 and the fragment notes, which is generally handled by the browser. An HTTP request has a method, target and headers, and may contain a body. The response carries a status, headers and often a body.

文档对象模型（Document Object Model, DOM） 把 HTML 表示成可读写的树。同源策略（Same-Origin Policy, SOP） 检查协议、主机和端口是否都相同。上例改成端口 443 就成了不同源。两个路径不同但协议、主机、端口相同，仍然同源。这个规则会限制跨源脚本读取和操作。某些跨源请求仍可发出，服务器要验证请求本身。

The Document Object Model (DOM) represents HTML as a readable and writable tree. The same-origin policy (SOP) checks whether scheme, host and port all match. Changing the example to port 443 changes the origin. Two paths can differ and still share an origin. SOP restricts cross-origin script reads and interactions. Some cross-origin requests can still be sent, so the server must validate actions.

Cookie 怎样维持会话

How cookies maintain sessions

HTTP 单次请求不会自然记住你登录过。服务端创建 会话（Session），把不能轻易猜出的 会话标识（Session ID） 通过 Set-Cookie 交给浏览器。浏览器在符合规则的请求中附上 Cookie，服务器据此读取会话状态。Cookie 只携带应用定义的值，权限仍由服务端决定。

An isolated HTTP request does not automatically remember a previous sign-in. The server creates a session and sends a hard-to-guess session ID through Set-Cookie. The browser includes the Cookie for requests that meet its rules. The server uses the ID to look up state and decides authorization.

属性 阅读时要理解的作用
Domain / Path 限制哪些主机或路径的请求携带 Cookie。父域配置过宽会扩大子域影响。Path 主要决定发送范围。
Secure 约束 Cookie 只通过安全连接发送。
HttpOnly 阻止页面脚本直接读取该 Cookie。符合规则的请求仍可携带它。
SameSite 约束跨站请求带 Cookie 的方式。Strict 最严格，Lax 允许一些安全的顶级导航，None 允许按其他规则用于跨站请求。
Expires / Max-Age 设定保存期限。会话是否继续有效也由服务器决定。
Attribute Purpose
Domain / Path Scope the hosts or paths that receive the cookie. A broad parent domain can increase subdomain influence. Path mainly limits sending.
Secure Send it over a secure connection.
HttpOnly Forbid direct reads by page scripts. Eligible requests can still carry it.
SameSite Controls cross-site inclusion. Strict is the most restrictive. Lax permits some safe top-level navigation. None allows inclusion subject to other rules.
Expires / Max-Age Control retention. The server still decides whether a session is valid.

同站（Same-Site） 与 DOM 的同源不是同一个判断。典型浏览器按方案与可注册域比较站点。子域不同可以是同站而不同源。会话固定（Session Fixation） 指登录前的标识被第三方掌握，登录后应用又沿用它。登录和提权后更新会话标识，退出时使服务端会话失效。

Same-site and DOM same-origin are distinct checks. Typical browsers compare scheme and registrable domain for site calculations. Different subdomains can be same-site while remaining cross-origin. Session fixation occurs when a third party knows the pre-login ID and the application keeps it after authentication. Rotate the ID on sign-in or privilege changes and invalidate the server session on logout.

CSRF 与点击劫持

CSRF and clickjacking

跨站请求伪造（Cross-Site Request Forgery, CSRF） 常出现在这样的组合。用户有有效登录状态，浏览器能向网站发出状态修改请求并带凭据，而服务端只检查「登录了吗」。即使攻击者读不到响应，修改也可能发生。讲义用改账号资料来解释。服务端需要核验 这一项操作是否经过授权。

Cross-site request forgery (CSRF) often combines a valid signed-in session, a browser that can send a state-changing request with credentials, and a server that checks only whether someone is signed in. Changes can occur even if the adversary cannot read the response. The slides illustrate this with account details. The server needs evidence that this particular action is authorized.

  • 防 CSRF 令牌（Anti-CSRF Token） 应难以猜到，并与合适的会话或请求上下文关联。正常界面把令牌作为额外字段送回，服务端独立验证。仅检查 Cookie 仍只说明浏览器带了会话。
  • Origin / Referer 检查与合适的 SameSite 设置可以共同限制不同路径。把 GET 改成 POST 只改变方法，服务端仍要验证令牌或来源。
  • 点击劫持（Clickjacking） 让用户以为点击了一个界面，实际操作另一个被嵌入的界面。CSP frame-ancestors 限制哪些页面有权嵌入敏感界面，处理的是显示与交互边界。
  • An anti-CSRF token should be hard to guess and bound to an appropriate session or request context. The normal interface returns it as an additional value that the server checks independently. A cookie check by itself indicates session credentials were sent.
  • Origin or Referer validation and appropriate SameSite settings can restrict different paths. A switch from GET to POST changes the method, and a token or origin check is still needed.
  • Clickjacking misleads the user about which embedded interface receives a click. CSP frame-ancestors restricts who can embed a sensitive page, protecting the presentation and interaction boundary.

答题顺序。先看浏览器会不会带这个 Cookie，再看服务器有没有检查操作来源，最后判断请求能否引起状态变化。

Exam reasoning. Ask whether the browser sends the cookie, whether the server checks the action's origin, and whether the request can change state.

反射型与存储型 XSS

Reflected and stored XSS

跨站脚本（Cross-Site Scripting, XSS） 是浏览器在受信站点的上下文中解释了本应作为数据的输入。反射型（Reflected） 把本次请求里的输入放进本次响应。存储型（Stored） 先把输入写进数据库或内容系统，以后每位打开相应页面的人都可能遇到。已有的站点权限可能让错误执行的脚本读取页面或代为发请求。

Cross-site scripting (XSS) occurs when a browser interprets untrusted data as executable content in a trusted site's context. Reflected XSS puts input from the current request into its response. Stored XSS saves input to a database or content system, so it can affect later visitors. Code running in that origin can use the site's privileges to read page data or send requests.

上下文相关输出编码（Context-Sensitive Output Encoding） 先看输出位置。HTML 正文、属性值、URL、脚本字面量各有不同规则。若页面只需显示一段文字，应使用文本接口或模板的安全默认输出。确实允许富文本时，使用有明确允许列表的 净化（Sanitization）。内容安全策略（Content Security Policy, CSP） 进一步约束允许执行的脚本。HttpOnly 有助于阻止脚本直接读取 Cookie，仍应修复可执行输入。

Context-sensitive output encoding starts by identifying the output position. HTML text, attribute values, URLs and JavaScript literals have different rules. For ordinary text, use a text API or the template's safe default. Where rich text is necessary, use sanitization with an explicit allowlist. A content security policy (CSP) can further restrict script execution. HttpOnly helps block direct cookie reads, while the executable input still needs correction.

SQL 参数化为什么有效

Why SQL parameterization works

SQL 注入（SQL Injection） 发生在服务器将不可信输入拼接到 SQL 串时。数据库解析的是整条字符串，无法仅凭来源知道每段是语法还是普通值。即使页面不展示直接的查询输出，错误差异和延迟也可能泄露信息。

SQL injection occurs when a server builds a SQL string by concatenating untrusted values. The database parses the whole string and cannot tell which parts the application meant to be values. Even without a direct result in the page, error differences or timings can leak information.

预处理语句（Prepared Statement） 把语句结构和输入值分开。先让数据库准备 SELECT name FROM users WHERE id = ?，再通过 参数绑定（Parameter Binding） 提供 id。数据库将 id 当一个值使用，查询语法事先固定。表名或排序字段属于结构，通常用服务端固定选项映射。用最小权限账号能缩小查询出错时的影响范围。

A prepared statement separates structure and values. First prepare SELECT name FROM users WHERE id = ?, then supply id through parameter binding. The database uses id as a value under an already established query structure. Table or sort-column names are structural and can be mapped from fixed server-side options. A least-privilege database role limits the impact of errors.

风险 失守的边界 主要防护
CSRF 从已认证会话到用户真实意图 令牌、来源检查、SameSite。
XSS 从页面数据到可执行内容 按上下文编码、富文本净化、CSP。
SQL 注入 从用户值到数据库语句结构 预处理语句、参数绑定、最小权限。
Problem Broken boundary Primary defenses
CSRF Authentic session versus real user intent Tokens, origin validation, SameSite.
XSS Page data versus executable content Contextual encoding, rich-text sanitization, CSP.
SQL injection Input value versus SQL statement structure Prepared statements, parameter binding, least privilege.
