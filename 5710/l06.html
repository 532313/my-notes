数字证书与公钥基础设施

Digital certificates and public-key infrastructure

把「算得出共享密钥」和「知道对方是谁」分成两件事。证书将身份与公钥绑定。你还要验证谁有权签发、证书现在能不能用，以及对端是否持有相应私钥。

Establishing a shared key and knowing who is on the other end are separate tasks. A certificate binds an identity to a public key. Check who can issue it, whether it can be used now, and whether the peer holds the corresponding private key.

为什么 DH 还需要身份认证

Why DH also needs authentication

裸 DH 让双方算出一个数学上的共享值。若交换的公开值没有可信身份绑定，一位 中间人（Man-in-the-Middle, MITM） 可能让双方误以为各自正在与预定对象通信。修复思路是签名覆盖这次交换的两个公开值和相关上下文，让双方验证是谁参与了本次交换。讲义用 站到站协议（Station-to-Station, STS） 说明一种认证密钥交换。

Plain DH establishes a mathematical shared value. If exchanged values are not authenticated, a man in the middle (MITM) may make each side believe it is talking to the intended peer. Bind this exchange's public values and relevant context into signatures that the parties can check. The slides illustrate an authenticated key exchange with Station-to-Station (STS).

验证者还要可信地取得签名公钥。公开广播依赖接收方另行核对发布者。目录依赖受信维护者。在线公钥权威可为查询响应签名。公钥证书（Public-Key Certificate） 把身份与公钥的绑定写进可验证的文件。客户端无须在每次交换时直接联系签发方来验证证书签名，仍要按策略检查证书状态。

The verifier still needs the authentic signature verification key. A broadcast relies on another way to check the publisher. A directory relies on its trusted maintainer. An online public-key authority can sign query responses. A public-key certificate expresses the identity-to-key binding in a verifiable document. Verifying its signature need not contact the issuer during every exchange, although status checks still follow policy.

长期身份密钥和每次连接协商的密钥承担不同角色。证书常用于认证长期身份。会话密钥（Session Key） 用于保护这一次会话的数据。

Long-term identity keys and fresh keys have different roles. Certificates often authenticate long-term identity. A session key protects the data for a particular session.

看懂 X.509 证书各字段

Reading X.509 certificate fields

字段 读法
Subject / Issuer 主体是证书描述的对象，签发者为签名负责。
SPKI（Subject Public Key Info） 主体公钥与算法标识。公钥可公开。
Serial Number / Validity 序列号帮签发者区分证书，有效期规定可接受的时间。
SAN（Subject Alternative Name） 可列出持证网站的域名。客户端拿访问的域名核对它。
Basic Constraints / Key Usage 说明是否可作为 CA、路径限制及允许用途。
Signature 签发者对待签证书内容的签名。
Field What to look for
Subject / Issuer The subject is described by the certificate. The issuer signs it.
Subject Public Key Info (SPKI) The subject's public key and its algorithm identifier.
Serial number / Validity The serial identifies a certificate for the issuer. The dates bound its validity.
Subject Alternative Name (SAN) Can list website DNS names. The client checks its requested name against the certificate.
Basic constraints / Key usage Indicate CA status, path restrictions and permitted uses.
Signature The issuer's signature over the to-be-signed certificate content.

撤销（Revocation） 处理有效期还没结束却应停止接受的证书，例如私钥泄露。证书吊销列表（Certificate Revocation List, CRL） 记录被吊销的序列号并有签名，核对时既看签发者，也看列表本身的有效时间。证书的有效期、签名、名称和吊销都要按适用策略检查。

Revocation handles a certificate that should no longer be accepted before expiry, for example after a key compromise. A signed certificate revocation list (CRL) records revoked serial numbers. Check the list's issuer and freshness as well as its signature. Validity, signatures, names and revocation are all subject to applicable validation policy.

证书链可以通过中间 CA 或交叉签发找到多个路径。路径验证要从叶证书走到客户端已经信任的锚。证书上写的「签发者名」是寻找验证公钥的线索，签名本身才证明这个绑定被相应私钥签过。

Intermediate CAs or cross-signing can create several possible paths. Validation builds a path from the leaf to an anchor the client already trusts. The issuer name helps locate a possible verification key. The signature proves that the corresponding private key signed the binding.

从生成密钥到签发证书

From generating a key to issuance

公钥基础设施（Public Key Infrastructure, PKI） 包括身份核验、证书签发、存储、验证与撤销。CA（Certification Authority） 签发证书。RA（Registration Authority） 可代为核验身份。持证服务器和用户是 终端实体（End Entities），依赖证书的一方称 验证方（Relying Party）。

Public key infrastructure (PKI) includes identity checks, issuance, distribution, verification and revocation. A certification authority (CA) issues certificates. A registration authority (RA) can assist with identity checks. Certificate holders are end entities, and parties that rely on their certificates are relying parties.

  1. 服务器生成公私钥，把公钥与所申请的身份写进 证书签名请求（CSR）。
  2. 申请者用自己的私钥在 CSR 中证明持有对应密钥。CA 还要另行核验其是否有权使用申请的域名。
  3. 核验通过后，CA 用 CA 私钥 签发证书。服务器部署证书和中间链，服务器私钥继续留在服务器的控制下。
  4. 握手时，服务器用这把私钥完成与握手相关的证明。把一张公开证书交给客户端，并不会自动完成持钥证明。
  1. The server generates a key pair and puts its public key and requested identity in a certificate signing request (CSR).
  2. The applicant uses its private key to prove possession in the CSR. The CA separately checks that the applicant may use the requested domain.
  3. After verification, the CA signs the certificate with the CA private key. The server deploys the certificate and intermediates and keeps its own private key under its control.
  4. During a handshake, the server completes a proof tied to that private key. Delivering the public certificate alone leaves possession unproved.

容易弄反的三把钥匙。CSR 用申请者公钥核验。证书签名用签发者公钥核验。握手中的对端持钥证明用证书绑定的公钥或套件相应机制核验。

Track three verification roles. Check a CSR with the applicant's public key, an issued certificate with the issuer's public key, and a handshake proof with the key bound to the peer or the mechanism chosen by its suite.

逐级验链与错误定位

Validate a chain and identify failures

设 R 是客户端受信根，I 是中间 CA，S 是服务器证书。用 I 的公钥验 S，用 R 的公钥验 I。信任锚（Trust Anchor） 来自本地信任配置。根的自签名能证明它与公钥相符，是否信任该根是单独的选择。

Let R be a client-trusted root, I an intermediate CA and S a server certificate. Verify S with I's public key and I with R's public key. A trust anchor comes from local trust configuration. A root's self-signature verifies with its own key, while trusting that root is a separate decision.

按次序检查。找能通向信任锚的链，验每条签名。检查签发者获准作为 CA，核对基本约束、有效期、用途和适用的吊销信息。核对 S 的主机名，再看握手是否提供持钥证明。路径长度题要按题意数 从属 CA，别把最终叶证书误数进去。

Check in order. Build a path to an anchor and verify each signature. Ensure an issuer is authorized as a CA. Check basic constraints, time, usage and applicable revocation status. Match S to the hostname and check for handshake proof of possession. When the question limits path length, count subordinate CAs under the stated rules. The final leaf is not a subordinate CA.

情境 判定
S 签名有效，但访问的域名不在 SAN 身份不匹配，拒绝。
中间 I 被设置成非 CA，却签发 S 缺少签发授权，拒绝。
I 的路径长度为 0，却多出一个下级中间 CA 超过了该约束，拒绝。
CA 签名私钥失陷 一些证书的密码学签名可能仍正确，但信任假设已被破坏，需要撤销或更新信任配置。
Scenario Result
S has a valid signature but its SAN lacks the requested domain Reject the identity mismatch.
I is marked as a non-CA but issued S Reject for lack of issuer authorization.
I has a path length of zero and a further intermediate CA appears below it Reject the path-length violation.
A CA signing key is compromised Signatures can remain mathematically valid while the trust assumption has failed. Revoke certificates or update trust as appropriate.
