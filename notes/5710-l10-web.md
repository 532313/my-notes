浏览器能发请求、带登录凭据和执行页面脚本。Web 安全题先看失守的边界在用户意图、浏览器解释页面，还是数据库解释语句。

## HTTP、URL 和同源（讲义第 1–8 页）

**统一资源定位符（Uniform Resource Locator, URL）** 包含协议、主机、可能的端口、路径、查询参数和片段。片段通常由浏览器使用，不随普通 HTTP 请求发送。**超文本传输协议（Hypertext Transfer Protocol, HTTP）** 让浏览器请求页面资源，服务器返回响应。请求包括方法、目标、头字段，有的还有请求体。

**文档对象模型（Document Object Model, DOM）** 把页面表示成供脚本读取、修改的对象树。**同源策略（Same-Origin Policy, SOP）** 比较 **源（Origin）** 的协议、主机和端口，限制跨源读取和脚本访问。两个页面只换端口便会变成不同源。某些跨源请求仍允许发出，所以「读不到响应」不能推出「请求发不出去」。

## Cookie 与会话管理（讲义第 9–21 页）

HTTP 本身没有跨请求的用户状态。**会话管理（Session Management）** 把请求和同一登录关联起来。服务器通过 `Set-Cookie` 写入 **Cookie**，浏览器在满足条件的请求里用 `Cookie` 头带回。持续的时间可由 **Expires** 或 **Max-Age** 决定。没有持久化期限的一般是会话 Cookie。

| 属性 | 主要约束 |
| --- | --- |
| **Domain / Path** | 控制哪些主机和路径的请求会携带这条 Cookie。范围过宽会增加其他子域影响会话的机会。 |
| **Secure** | 限制通过安全连接发送。 |
| **HttpOnly** | 限制页面脚本直接读取。浏览器仍可在符合条件的请求中携带。 |
| **SameSite** | 调整跨站请求是否附上 Cookie。与 DOM 按协议、主机、端口判同源的规则分开理解。 |

**会话固定（Session Fixation）** 涉及用户登录后仍沿用登录前已被第三方掌握的会话标识。保护措施包括使用难预测的标识、登录后更新标识、合理缩小 Cookie 的作用域。URL 中携带会话标识更容易进日志或分享链接，课件将它与表单和 Cookie 机制对比。

## CSRF 与点击劫持（讲义第 22–37 页）

**跨站请求伪造（Cross-Site Request Forgery, CSRF）** 让已登录用户的浏览器发起未经用户同意的状态变更。条件是浏览器能发出该请求、附上可用凭据，而服务器没有核验请求来自预期交互。讲义用更改账户资料的例子说明，即使对方看不到返回页面，状态也可能已改变。

- **防 CSRF 令牌（Anti-CSRF Token）** 由服务器生成并验证。正常页面可以把令牌随表单或请求头送回来，跨站页面难以在符合浏览器隔离的前提下取得它。令牌与当前会话关联。
- 可结合 **Origin / Referer** 检查来源，按操作选择合适的 **SameSite** 策略。对修改状态的接口做服务器端检查。仅把 GET 改成 POST 并不能确认用户意图。
- **点击劫持（Clickjacking）** 在界面上让用户看到一个目标、实际点中另一个。限制谁能嵌入敏感页面，例如通过 CSP 的 **frame-ancestors**，针对的就是这一层。

## XSS 让数据变成浏览器代码（讲义第 38–49 页）

**跨站脚本（Cross-Site Scripting, XSS）** 源于页面把不可信数据解释成有执行能力的内容。**反射型 XSS（Reflected XSS）** 的内容来自当前请求并进入当前响应。**存储型 XSS（Stored XSS）** 的数据先被站点保存，其他人后来打开页面也可能遇到。讲义的 Samy 蠕虫案例说明，存储型问题可能随用户页面传播。

主要防护是按输出位置做 **上下文相关编码（Context-Sensitive Output Encoding）**。HTML 文本、属性、URL 和脚本使用不同规则。确实允许用户提交少量 HTML 时，用经过审查的 **净化（Sanitization）** 机制。**内容安全策略（Content Security Policy, CSP）** 还可减少浏览器允许执行脚本的位置与来源。依靠屏蔽某一个标签的过滤容易漏掉其他解释方式。

## SQL 注入让输入改变查询（讲义第 50–61 页）

**SQL 注入（SQL Injection）** 发生于服务端把外部值拼进 SQL 字符串，导致输入改变语句结构。即使页面不返回详细查询结果，也可能从错误、页面差异或耗时暴露信息。

**预处理语句（Prepared Statement）** 与 **参数绑定（Parameter Binding）** 先让数据库处理固定查询结构，再把用户输入作为值传入。比如先准备 `SELECT name FROM users WHERE id = ?`，再绑定 id。用户提供的值不会成为可执行的 SQL 片段。表名或排序字段这类结构位置应通过固定选项映射，数据库连接也应只使用必需的权限。

## 自查

1. 哪种 Cookie 属性限制脚本读取？哪种影响跨站请求是否携带？
2. 把 CSRF、XSS 与 SQL 注入分别归到「请求意图」「页面内容解释」「查询结构」三个边界。
3. 为什么参数绑定能保护值的位置？如果用户可以选择排序字段，还要检查什么？
