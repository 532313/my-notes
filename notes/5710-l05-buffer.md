缓冲区只占一段有限的内存。写入超过容量时，程序除了可能崩溃，还可能改坏紧挨着的变量、指针或控制数据。这一讲先学会读内存图，再检查哪里缺了边界。

## 从程序文件到进程内存（讲义第 1–21 页）

**程序（Program）** 是指可执行指令和数据。**进程（Process）** 是运行中的实例，拥有独立的资源及 **虚拟地址空间（Virtual Address Space）**。相同的虚拟地址可以在不同进程里映射到不同物理内存。操作系统按 **页（Page）** 映射并设定权限。课件举了 **页对齐（Page Alignment）** 与 **直接内存访问（Direct Memory Access, DMA）** 的例子，说明硬件接口可能要求某种地址边界。

| 区域 | 常见内容 |
| --- | --- |
| **代码段（Text Segment）** | 机器指令，通常页可执行且不可写。 |
| **数据段（Data Segment）** | 有初值、需要保存在程序文件里的可写全局变量和静态变量。 |
| **BSS（Block Started by Symbol）** | 启动时为零的全局或静态存储，文件主要记录需要多大空间。 |
| **堆（Heap）** | 动态分配。分配器也可能通过独立的内存映射取得大块空间。 |
| **栈（Stack）** | 调用信息和部分局部变量。课件的 x86 示例从高地址向低地址增长。 |

**缓冲区（Buffer）** 是有容量的一段连续存储，例如字节数组。C 的普通指针只有地址信息。一次写入能否落在数组里，要结合容量和偏移检查。传递 C 数组参数时通常得到指向首元素的指针，接收方还需要单独知道容量。深递归或巨大局部数组可能把栈空间用尽，称为 **栈耗尽（Stack Overflow）**。

## 一次函数调用怎样来回（讲义第 22–50 页）

**栈帧（Stack Frame）** 是某次函数调用在栈上使用的区域。讲义的 32 位 x86 模型包含下面三个阶段。

1. 调用者（Caller）准备参数。**调用指令（CALL）** 在栈上存放下一条指令的地址，再跳到被调函数（Callee）。
2. 被调函数保存原帧指针，建立新帧并给局部数据留空间。**栈指针（Stack Pointer, ESP）** 随压栈和弹栈变化，**帧指针（Frame Pointer, EBP）** 可以作为查找本帧的固定参照。
3. 结束时恢复帧信息。**返回指令（RET）** 读取保存的返回地址，指令指针 EIP 随后回到调用者。多次嵌套调用会依次建立、退出各自的帧。

**调用约定（Calling Convention）** 规定参数怎么传、谁保存哪些寄存器、谁清理栈上的参数。课件比较了 32 位 x86 的 `cdecl` 与 `stdcall`。开启优化或换体系结构后，寄存器、填充和实际帧布局都可能变化。做图题要按题给模型写偏移与字节范围。

## 漏洞成因与影响（讲义第 51–80 页）

**缓冲区溢出（Buffer Overflow）** 是数据跨过分配边界。读讲义的典型案例时，先从函数调用链找到接收数据的局部缓冲区，再判断哪一处复制没有检查实际容量。字符串还要为 **空终止符（NUL Terminator）** 预留一个字节。

越界写先破坏相邻数据。若碰到保存的返回地址等 **控制数据（Control Data）**，还可能改变控制流。讲义的 **注入代码（Shellcode）** 案例展示了在缺少保护的历史实验模型中，进程为何可能执行并非原程序的指令。远程输入进入同样的复制路径，也会扩大漏洞影响范围。实际后果取决于内存页权限、程序权限和沙箱边界。即使没有立刻触发段错误，越界已经发生。

## 从代码修复到系统防护（讲义第 81–85 页）

| 措施 | 具体检查或限制 |
| --- | --- |
| **边界检查（Bounds Checking）** | 写前比较完整长度与容量。16 字节的 C 字符串数组最多容纳 15 字节内容和一个 NUL。使用有长度参数的 API 时，还要处理截断与终止符。 |
| **栈金丝雀（Stack Canary / StackGuard）** | 函数返回前检查放在敏感数据附近的值是否被改动。 |
| **地址空间布局随机化（Address Space Layout Randomization, ASLR）** | 改变映射位置，降低对内存布局的可预测性。 |
| **可写与可执行互斥（Write XOR Execute, W^X）** | 限制页同时可写和可执行，通常让用户栈可写且不可执行。 |

代码修复解决写出边界的问题。编译器和操作系统的措施各自约束后续影响，所以应同时保留。堆上的数组也要检查容量和生命周期。
